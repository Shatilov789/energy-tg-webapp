# PROCESSES.md — Бизнес-процессы Energy CRM

Описание всех процессов системы: кто делает, что происходит, какие права.
Файл для синхронизации понимания между разработкой и продуктом.

---

## Роли

| Роль | Описание |
|------|----------|
| **Admin** | Полные права: создаёт пользователей, управляет ответственными, блокирует/разблокирует ответы, комментирует от имени администрации, видит все объекты |
| **Worker** | Сотрудник: создаёт объекты, заполняет комментарии к этапам, пишет в обсуждения, управляет критичностью своих объектов |

---

## 1. Регистрация пользователя

**Кто:** Только Admin  
**Как:** AdminPage → таб "Пользователи" → кнопка `+` (IconUserPlus) → модалка

**Шаги:**
1. Admin идёт в Telegram, просит сотрудника прислать свой `/myid` боту
2. Admin вводит: Telegram ID, имя, фамилию (необязательно), username (необязательно), роль (Сотрудник / Администратор)
3. `POST /admin/users` → создаётся User
4. Сотрудник может войти в Web App — система узнаёт его по Telegram ID

**Деактивация пользователя:**
- Admin нажимает замок на карточке пользователя
- `PATCH /admin/users/{id}/toggle-active` → is_active меняется
- Себя деактивировать нельзя (кнопка disabled)
- Деактивированный пользователь не может войти (401)

**Важно:** Без регистрации Admin'ом войти нельзя.

## 2. Создание объекта инспекции

**Кто:** Worker (или Admin)  
**Как:** HomePage → кнопка молнии (FAB) или таб "Создать" → ObjectsPage

**Шаги:**
1. Выбирается сценарий (шаблон вопросов) через кастомный dropdown с иконками
2. Вводится название объекта + необязательный комментарий
3. `POST /api/objects/` → создаётся Object (status=in_progress, criticality=normal)
4. Создатель автоматически добавляется как ответственный в `object_workers`
5. Объект появляется в HomePage

**Результат:** Object (status=in_progress, criticality=normal), создатель = первый ответственный.

---

## 3. Критичность объекта

**Кто:** Ответственный за объект (ObjectWorker) + Admin  
**Как:** HomePage → карточка → бейдж критичности → тап → модалка выбора

**Уровни:**

| Уровень | Значение | Цвет бейджа | Порядок в списке |
|---------|----------|-------------|-----------------|
| `normal` | Штатный режим | Серый | Последними |
| `high` | Требует повышенного внимания | Оранжевый | После critical |
| `critical` | Критическая ситуация | Красный | Первыми |

**API:** `PATCH /objects/{id}/criticality` — тело `{"criticality": "high"}`

**Сортировка:** critical → high → normal → по дате обновления (и на главной, и в Админ).

**Лог:** Изменение критичности записывается в журнал объекта с деталями "Норма → Критический".

## 4. Управление ответственными за объект

**Кто:** Admin  
**Как:** AdminPage → карточка объекта → строка ответственных → "+" или "×"

**Добавить ответственного:**
1. Admin нажимает "+" у объекта
2. Выбирает сотрудника из списка
3. `POST /admin/objects/{id}/workers/{user_id}` → строка в `object_workers`
4. Сотрудник видит объект в своей HomePage

**Убрать ответственного:**
1. Admin нажимает "×" у тега сотрудника
2. `DELETE /admin/objects/{id}/workers/{user_id}` → строка удаляется
3. Сотрудник теряет доступ

**Права после добавления:**
- Видит объект в HomePage
- Заполняет "Комментарий к этапу"
- Пишет в "Обсуждение шага"
- Может менять критичность

**По умолчанию:** Создатель объекта автоматически ответственный.

## 5. Прохождение этапов (шагов) объекта

**Кто:** Ответственные (ObjectWorkers) + Admin  
**Как:** HomePage → карточка объекта → переход на StepPage

Каждый шаг содержит **два независимых блока:**

### 5.1 Комментарий к этапу (верхний блок)

**Кто пишет:** Только ответственные + Admin

**Правила:**
- Первый раз: пустое поле → сотрудник пишет → "Сохранить" → `POST /objects/{id}/steps/{step_id}/answer`
- Дополнение: существующий текст **readonly**, ниже поле "Дополнить..." → `PUT` (текст конкатенируется через `\n\n`)
- Admin может заблокировать ответ (`is_locked=True`) → поле дополнения исчезает
- Кнопка "Далее" активна только если комментарий сохранён

**API:**
- Первое: `POST /objects/{id}/steps/{step_id}/answer`
- Дополнение: `PUT /objects/{id}/steps/{step_id}/answer`
- Блокировка (Admin): `PATCH /admin/answers/{id}/lock`
- Разблокировка (Admin): `PATCH /admin/answers/{id}/unlock`

### 5.2 Обсуждение шага (нижний блок)

**Кто пишет:** Все с доступом к объекту (ответственные + Admin)

**Правила:**
- Тред-сообщения: можно цитировать (reply_to_id)
- Упоминание коллеги отправляет ему уведомление
- Системные события отображаются курсивом: "Заблокировано", "Разблокировано", "Администратор оставил комментарий"

**API:**
- `GET /objects/{id}/steps/{step_id}/comments`
- `POST /objects/{id}/steps/{step_id}/comments` (reply_to_id, recipient_id — опционально)

## 6. Навигация по шагам

**Кто:** Ответственные + Admin

**Навигация:**
- Кнопки `‹` / `›` + счётчик "5 / 10"
- Свайп влево/вправо (touch events)
- "Далее" заблокирован пока комментарий не сохранён (для ответственных)
- Admin листает без ограничений
- Последний шаг → кнопка "Отправить отчёт" → возврат на главную

## 7. Журнал изменений объекта

**Кто:** Все с доступом к объекту (ответственные + Admin)  
**Как:** HomePage → карточка → "История" (ссылка в строке мета)  
**Маршрут:** `/objects/:id/log`

**Показывает (новые первыми, группировка по дате):**

| Событие | Когда |
|---------|-------|
| Объект создан | При создании |
| Ответ добавлен | При первом сохранении шага |
| Ответ обновлён | При дополнении шага |
| Критичность изменена | При смене уровня (показывает "Норма → Высокий") |
| Ответственный добавлен/убран | При добавлении/удалении через Admin |
| Комментарий добавлен | При admin-комментарии к ответу |
| Шаг разблокирован | При разблокировке Admin'ом |
| Статус добавлен | При добавлении status note к шагу |

**API:** `GET /objects/{id}/audit` — лимит 500 записей

**Принцип:** Все события логируются через `log_action(..., object_id=X)`. Любая будущая фича, вызывающая `log_action` с `object_id`, автоматически появляется в журнале.

## 8. Администрирование ответов

**Кто:** Admin  
**Как:** AdminPage → таб "Объекты" → карточка объекта → список ответов

**Действия:**
- **Заблокировать** (`PATCH /admin/answers/{id}/lock`) — readonly для Worker, системное событие "lock", уведомление сотруднику
- **Разблокировать** (`PATCH /admin/answers/{id}/unlock`) — Worker снова может дополнять, системное событие "unlock", уведомление
- **Комментарий** (`POST /admin/answers/{id}/comment`) — Admin пишет комментарий к ответу, Worker видит под полем, приходит уведомление

---

## 9. Уведомления

**Получает:** Worker (и Admin при упоминании)

| Событие | Тип | Получатель |
|---------|-----|-----------|
| Admin заблокировал ответ | step_unlocked | Worker-автор ответа |
| Admin разблокировал ответ | step_unlocked | Worker-автор ответа |
| Admin оставил комментарий | admin_comment | Worker-автор ответа |
| Упоминание в обсуждении | step_comment | Упомянутый пользователь |
| 2 дня без активности | reminder | Ответственные объекта |

**Прочтение:** Тап на уведомление → переход на шаг объекта → уведомление отмечается прочитанным.  
Красная точка на таббаре показывает количество непрочитанных.

## 12. Технические примечания

**Аутентификация:**
- Prod: Telegram `initData` в заголовке `X-Telegram-Init-Data`
- Dev: заголовок `X-Dev-Telegram-Id: 567835393` (admin) или `987654321` (worker)

**Audit log принцип:**
- Все действия вызывают `log_action(db, user_id=..., action=..., entity_type=..., entity_id=..., object_id=...)`
- `object_id` обязателен для всех действий связанных с объектом — это обеспечивает попадание в журнал
- Действия без `object_id` (регистрация пользователей) в журнал объекта не попадают

**DB enum workaround:**
- SQLAlchemy создаёт PostgreSQL enum с uppercase именами (`NORMAL`, `HIGH`, `CRITICAL`)
- Python enum хранит lowercase значения (`"normal"`, `"high"`, `"critical"`)
- Маппинг автоматический: DB `"NORMAL"` → Python `ObjectCriticality.NORMAL` → API `"normal"`
- При добавлении нового enum значения нужно: 1) добавить в Python enum, 2) `ALTER TYPE ... ADD VALUE '...'` в PostgreSQL
